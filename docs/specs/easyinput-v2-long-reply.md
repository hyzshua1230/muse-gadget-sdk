# EasyInput 长等待与长回复语音修复

日期：2026-10-11。替代早期语音规格中60秒无进展、180秒总时长、整条PCM收齐后播放的限制。

## 问题与修改

- 搜索/思考期间允许连续300秒没有回复进展。收到相关消息或agent/task状态更新重新计时；连接失效仍由原有网络检测报错。
- 云端任务总等待上限900秒，超过时明确报错，不再把半条回复标为成功完成。
- 正在本地合成或输出音频时不适用云端等待计时。每次合成的HTTP等待上限90秒、下载仍限10秒，不新增自动重试或供应商降级。90秒是HTTP等待上限，不是整轮绝对时长保证。
- 完整消息文本容量从8192提升至32768字节（含终止符，8消息约256KiB PSRAM）。超过容量明确报错，不截断文字。
- 消息完成后按最多200个UTF-8字符分段；长段优先在80字符后的句末切分。每段合成并交给播放器后处理下一段，不再累计整条回复PCM才开始朗读。分段间仍可能等待下一次合成，不承诺连续无停顿。
- 每段音频限制4MiB；整条首次朗读不再受4MiB累计限制。重播缓存仍限4MiB，索引容量改为64个音频段。超限或内存不足时缓存不可用，但不影响继续朗读；因此特别长的回复不保证S3续播/重播。
- S4暂停、S3续播、S1发起新提问沿用既有逻辑；暂停时继续接收并生成剩余段，完整缓存就绪后才能续播。

## 验证目标

1. 等待超过60秒和180秒、仍有搜索/思考进展的回复不会被提前取消。
2. 无任何进展持续300秒明确报错；持续忙碌且未完成的云端回复到900秒明确报错。
3. 本地音频合成/输出不因上述云端时间上限而中断。
4. 超过8191字节的文本在32767字节内正常分段；各段UTF-8完整且按顺序，不遗漏、不重复。
5. 超过4MiB累计音频仍完成首次朗读；缓存不足有明确日志。
6. 短回复以及缓存容量内的暂停/续播和播完重播保持可用。

## 重播缓存内存优化（2026-10-11）

用户要求优化S3重播的可用性。针对上轮约80秒音频仍释放缓存的实际日志，修改`muse_qwen_tts.cpp`：

- 已知HTTP Content-Length时按实际长度分配，超过下载上限立即失败；分块传输按256KiB步长增长，避免把约1至2MiB音频缓冲翻倍扩张至4MiB。
- 每段WAV解析成功后，在原缓冲中移除头部，直接转交PCM所有权，并收缩到有效音频长度；不同时持有两份完整音频。仍检查PCM16/24kHz/单声道、非空、偶数字节及4MiB上限。
- 保留已有多段追加路径、90秒合成等待、10秒下载等待、分段播放和缓存4MiB上限。未新增自动重试、Flash音频存储或音频格式变化。
- 验收目标：缓存容量内的较长回复能保留完整缓存；首次朗读结束S3从头重播，S4暂停后S3从中断位置继续；日志不再出现本案例中的`REPLAY CACHE NO MEMORY`。
